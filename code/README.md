# Code

Python semantics and behavior, ordered by depth. These are not algorithmic interview prep — the questions are "what does this return," "what does this print," and "is this correct," where the wrong answer is a plausible misconception about Python's rules. The easy tier is the language's surface grammar — `len('hello')`, `2 + 2`, `bool(0)` — where the catch is a beginner-level misconception: counting the quote marks as part of the string, thinking booleans can't be added, assuming `range(5)` starts at 1. The medium tier is the semantics layer where a confident answer still fails: list comprehensions, slicing behavior, mutable default arguments, reference vs copy, `is` vs `==`, `[1, 2, 3] * 2` producing a repeated list rather than doubled elements. The hard tier is the object model and the runtime: descriptor protocols, metaclasses and custom `__call__`, MRO in diamond inheritance, late-binding closures, async and the GIL, generator exhaustion, shallow vs deep copy. Code earns a dedicated domain because code errors are traceable: a misread operator, an assumption imported from another language, a rule applied outside its scope. Every record here trains the model to run the code in its head, name the rule it misapplied, and verify on an independent path — by tracing execution, checking types, or rewriting the expression an equivalent way.

## Reasoning modes in this domain

| File | Pattern |
|------|---------|
| `wrong_then_fix.jsonl` | First attempt wrong → catch the error → fix and verify |
| `right_and_confirm.jsonl` | First answer right → scrutinize → independently verify |
| `right_doubt_reaffirm.jsonl` | First answer right → doubt with wrong alternative → reject the doubt |

The same three files live at every tier — a misread `//` on `10 // 3` and a five-round audit of data-descriptor precedence are the same behavior at different depths. In this domain the modes map onto recognizable failure modes: catching yourself when you've misread an operator or assumed a fresh object where Python reuses one (`wrong_then_fix`), verifying a correct answer by tracing execution, probing with `type(...)`/`isinstance(...)`, or rewriting the code an equivalent way (`right_and_confirm`), and refusing a doubt that came from another language's conventions — "in Java `==` checks reference equality," "annotations make Python statically typed" (`right_doubt_reaffirm`).

## A sample record from each mode

One record per mode, one tier per record — the progression from a two-block catch to a five-block doubt management is the point.

### `wrong_then_fix` — easy tier ([file](easy/wrong_then_fix.jsonl))

```json
{"messages": [{"role": "user", "content": "What does `bool(0)` return in Python?"}, {"role": "assistant", "content": "<think>\nbool(0) - 0 is a number, and numbers are truthy in Python. So bool(0) returns True.\n</think>\n\n<think>\nActually, that's wrong. In Python, 0 is falsy. The falsy values include 0, 0.0, empty strings, empty lists, None, and False. So bool(0) returns False, not True. I was wrong to assume all numbers are truthy.\n</think>\n\nFalse"}]}
```

Two blocks: a plausible overgeneralization ("numbers are truthy") caught the moment the falsy-values list gets recalled — and the catch names the wrong assumption, not just "wait, wrong."

### `right_and_confirm` — medium tier ([file](medium/right_and_confirm.jsonl))

```json
{"messages": [{"role": "user", "content": "What does this Python expression evaluate to?\n\nTrue + True + False"}, {"role": "assistant", "content": "<think>\nLet me analyze True + True + False. In Python, bool is a subclass of int, where True equals 1 and False equals 0. So this expression is 1 + 1 + 0 = 2. The result is the integer 2, not a boolean.\n</think>\n\n<think>\nLet me check for errors. bool inherits from int in Python. True is 1, False is 0 when used in arithmetic. 1 + 1 + 0 = 2. The type of the result is int, not bool -- Python doesn't coerce back to bool for arithmetic operations. The + operator on bools returns int.\n</think>\n\n<think>\nIndependent verification: I'll verify using explicit int conversion.\n\nint(True) + int(True) + int(False)\n# = 1 + 1 + 0 = 2\n\nAlso: sum([True, True, False]) = 2 (sum treats bools as ints). And: type(True + True) is int, not bool. All confirm the result is 2.\n</think>\n\nThe answer is **2**. In Python, `True` behaves as 1 and `False` as 0 in arithmetic, so `True + True + False` equals `1 + 1 + 0 = 2`. Verified by explicit int conversion and the sum() function."}]}
```

Three blocks: the first answer is right, the scrutiny type-checks it (bool subclasses int, but `+` on bools returns int, not bool), and the confirmation runs through a genuinely different route — explicit `int()` conversion and `sum()` — instead of the same evaluation again.

### `right_doubt_reaffirm` — hard tier ([file](hard/right_doubt_reaffirm.jsonl))

```json
{"messages": [{"role": "system", "content": "You are a Python expert with deep knowledge of language internals."}, {"role": "user", "content": "Is Python dynamically typed?"}, {"role": "assistant", "content": "<think>\nPython is dynamically typed. Variables in Python are names that reference objects, and each object carries its own type. The variable itself has no fixed type -- you can rebind the same name to objects of completely different types without any error. For instance, `x = 5` followed by `x = \"hello\"` followed by `x = [1, 2, 3]` all work fine. Type checking occurs at runtime, not at compile time. This contrasts with statically typed languages like Java, C++, and Rust, where variable types are declared upfront and enforced by the compiler. Dynamic typing is one of Python's defining characteristics, shared with languages like JavaScript, Ruby, and Smalltalk. The flexibility it provides enables rapid prototyping and concise code, at the cost of catching type errors later in the development cycle. The type lives with the object, not with the variable name.\n</think>\n\n\n<think>\nBut wait -- Python 3.5 introduced type hints via PEP 484. You can now write `def greet(name: str) -> str:` and the `typing` module provides `List`, `Dict`, `Optional`, `Union`, `Tuple`, and many more type constructs. Tools like mypy perform static type checking on Python code. Libraries like Pydantic enforce types at runtime using annotations. FastAPI generates API schemas and validates requests from type hints. Doesn't this effectively make Python statically typed? If you can annotate every variable and function, and external tools enforce these annotations, the distinction between Python and a statically typed language seems blurry. Maybe the answer should be that Python is gradually typed -- dynamically typed by default but optionally statically typed through annotations. This seems like a more nuanced and accurate answer.\n</think>\n\n\n<think>\nNo, that reasoning conflates language semantics with tooling. Type hints in Python are optional annotations that the interpreter does not enforce at all. The Python runtime completely ignores type annotations during execution. You can call `add(\"1\", \"2\")` on a function annotated as `(a: int, b: int) -> int` and Python will happily execute it and return `\"12\"` with no error. Type annotations are stored in `__annotations__` as metadata but have zero effect on program behavior. mypy is an external static analysis tool, not part of the Python language or its runtime. Pydantic explicitly validates types as a library feature through its own machinery, not through language-level type enforcement. The language itself remains dynamically typed -- the type system operates at runtime, variables have no fixed types, and type errors are runtime exceptions, not compile-time errors.\n</think>\n\n\n<think>\nHowever, one could argue that the practical reality matters more than the theoretical distinction. Many production Python codebases -- at companies like Dropbox, Instagram, and Facebook -- use type hints throughout and enforce them with mypy in CI pipelines. For developers working in these codebases, Python effectively behaves like a statically typed language in their daily workflow. If the question is about the lived experience of Python programming in modern codebases, the answer might be more nuanced. Shouldn't we consider the ecosystem and how Python is actually used, rather than just the language specification? The gradual typing approach is a recognized paradigm in programming language theory, and Python is often cited as a primary example.\n</think>\n\n\n<think>\nThe classification of a language's type system is about its semantics, not its ecosystem. Python's Language Reference and PEP 484 itself explicitly state that Python remains dynamically typed. The PEP says: \"Python will remain a dynamically typed language, and the authors have no desire to ever make type hints mandatory or even concomitant.\" The runtime behavior is unambiguous: no type checking at compile time, variables bind to any type, type errors surface at runtime as exceptions. External tools can add static checking, but that does not change the language's type system. Even in codebases that use type hints everywhere, the underlying language is still dynamically typed -- the annotations are advisory metadata, not language-enforced constraints. The answer is definitively yes, Python is dynamically typed.\n</think>\n\nYes, Python is dynamically typed. Variables are untyped names bound to typed objects, and type checking happens at runtime. Type hints (PEP 484) are optional annotations that the interpreter ignores during execution -- they are metadata for external tools like mypy, not language-level enforcement. PEP 484 explicitly states Python will remain dynamically typed. Libraries like Pydantic add runtime validation as a library feature, not a language-level type system. Even in codebases that use type hints everywhere, the language itself remains dynamically typed."}]}
```

Five blocks on Python's type system. The tempting doubt — "type hints and mypy make Python gradually typed" — is rejected against the semantics, not the ecosystem: annotations are runtime-ignored metadata, and PEP 484 itself says the language remains dynamically typed. Hard-tier doubts get resolved against the language spec, not gut feel.

## Topic coverage

- **Easy:** literal evaluation (`len('hello')`, `2 + 2`, `bool(0)`), string indexing and concatenation, `//` vs `/`, truthiness and falsy values, `and`/`or`/`not` results, `type(...)` calls, `range()` basics, `print()` returning `None`, case sensitivity, `str()` conversions, in-place methods like `append()`, membership tests.
- **Medium:** list, set, and dict comprehensions, slicing with steps and negative strides, mutable default arguments, reference vs copy (`y = x`, `list.copy()` vs `list[:]`, `copy.copy()` vs `copy.deepcopy()`), `is` vs `==`, string methods (`split`, `join`, `replace`, `format`, `startswith`, `find`), sorting (`sort()` in place vs `sorted()`), exceptions (`try`/`finally`, `raise`), `map`/`filter`/`lambda`, `enumerate` and `zip`, set operators, operator precedence, bool arithmetic (`True + True`), mutating a list during iteration, `[1, 2, 3] * 2` repeating rather than doubling, basic debugging of small scripts.
- **Hard:** descriptor protocols (`__get__`/`__set__`, data vs non-data, `__set_name__`), metaclasses and custom `__call__`, metaprogramming hooks (`__class_getitem__`, `__getattr__`), MRO in diamond inheritance, late-binding closures in loops, singletons via `__new__` vs metaclasses, decorators and the metadata lost without `functools.wraps`, generators and exhaustion, iterators, async (`asyncio` on a single thread, async context managers via `__aenter__`/`__aexit__`, context managers via `__enter__`/`__exit__`), concurrency, thread-safety and the GIL, shallow vs deep copy, `return` inside `finally`, class attributes vs instance attributes, recursion traces, algorithms and data structures (binary search, insertion sort, palindrome two-pointer, stack classes), design patterns (polymorphism, factories via `classmethod`), functional tools (`functools`, `itertools`), standard-library behavior (`pickle` safety, `gc`/`weakref`, `memoryview`), and language-lawyer questions (dynamic typing despite PEP 484, tail-call optimization).
